# ADR 0006 — Versioning and release strategy

Status: accepted — 2026-05-30

## Context
The project must be made consumable by other projects, both as a **library**
(`github.com/giovibal/intreccio`) and as a **CLI** (`cmd/intreccio`). We need to fix:
(a) the versioning strategy and the git tag conventions, (b) the build and binary
publishing mechanism, (c) the level of automation. Current state: no tags, no
version plumbing in the binary, CI already in place (build, vet, `go test -race`,
lint), pure Go code with no cgo, a small and stable public API, but an on-disk
storage format **not yet frozen** and a bbolt adapter still planned.

## Decisions

### SemVer with `v` prefix, starting at `v0.1.0`
- **Annotated** tags `vMAJOR.MINOR.PATCH` (required by Go modules for
  `go get ...@vX.Y.Z`). Pre-releases with the `-rc.N` suffix.
- We start **pre-1.0** (`v0.1.0`). Rationale: in the `0.x` range SemVer allows
  breaking changes with a **minor** bump, an honest signal for a DB still
  evolving (storage format not frozen, bbolt adapter planned, growing Cypher
  coverage). No `v1.0.0` until these things stabilize.
- Pre-1.0 bump rule: breaking → minor (`0.2.0`); fix/backward-compatible addition
  → patch (`0.1.1`).

### Cross-platform build in the Makefile (Go toolchain only)
- `make dist` target: cross-compiles the CLI for every `linux/darwin/windows ×
  amd64/arm64` target with `CGO_ENABLED=0` (enforces the no-cgo invariant and
  makes cross-compilation possible without a C toolchain). `-trimpath` and
  `-ldflags` to inject version/commit/date into `main`. Artifacts: raw
  per-platform binaries; `make checksums` produces `checksums.txt` (SHA-256).

### Release on GitHub via GitHub Actions
- `release.yml` workflow on a `v*` tag push: **tag → test (`go vet` +
  `go test -race`) → `make dist checksums` → `gh release create`**. Release notes
  generated by `gh --generate-notes` (no conventional-commits requirement). Tags
  with `-rc/-beta/-alpha` become pre-releases.
- The `gh` CLI is preinstalled on the runners: no installation step.

### Explicit choice: no goreleaser, no Docker, no tools to install
- goreleaser was evaluated and discarded. Rationale: reduce dependencies, keep a
  reproducible build with the **Go toolchain only**, and simplify maintenance.
  The build logic lives in the Makefile and the orchestration in the workflow;
  both use only `go`, `make` and `gh`.

## Consequences
- A library consumer gets the version right after the tag push via the module
  proxy (`go get ...@v0.1.0`); no artifacts need to be published for library use.
- Publishing is entirely driven by the tag: no manual step, a single trigger
  point.
- Legal prerequisite handled separately: the **MIT** license (`LICENSE`), without
  which the code would not be importable.
- Future extensions (tar.gz/zip archives, Homebrew tap, Docker images, OS
  packages) stay out of scope; they can be added later without changing the
  strategy.
